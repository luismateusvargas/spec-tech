# Review a game feature

1. Identify the intended diff; read the Markdown task spec and its YAML project, constitution, and relevant domain definitions, plus linked designs, changed code and assets, affected systems, and tests. If the implementation used the SDD engine, call `get_run_report` and inspect its scope report, including undeclared paths and flags. Retrieve relevant Caipira history when available; verify current engine and platform facts independently. Flag work that relied on an unresolved required field.
2. Map each acceptance criterion to implementation and evidence. Inspect gameplay state, asset references, save or content compatibility, replication, accessibility, and frame or memory budgets where affected. Follow integration paths beyond changed files.
3. Run relevant automated, editor, build or cook, and in-game checks. Use target devices and measurements when available; distinguish them from editor-only or simulated results. Record platform and visual checks that could not run.
4. Judge every scope finding against the spec and actual diff. Record necessary additions as spec gaps; treat unjustified changes as findings with a counter-plan to revert them. A flag asks for inspection and is not proof of a defect. Report findings first by severity with code or asset location, triggering scenario, impact, evidence, and correction. State criterion and platform coverage plus remaining risks. If a criterion fails or a regression is confirmed, create a separate [counter-plan](../sdd-shared/templates/review.counter-plan.template.md) beside the original task spec, following the project's naming convention (otherwise `<task-stem>.counter-plan.md`). Tie every correction to a finding and its reproducing evidence; include only the smallest code or content changes and target checks needed to fix those failures. Mark blockers explicitly and do not turn unverified behavior into a repair task. Report its path. If no findings are supported, say so with limits; edit code only if fixes were requested.
5. Check the baseline and completion SHAs, then follow the [project-local Git checkpoint workflow](../sdd-shared/templates/git-checkpoints.md). On fully verified approval, tag the reviewed completion commit locally and report its name and SHA. Leave failures or incomplete verification untagged.
